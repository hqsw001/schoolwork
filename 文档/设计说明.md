### 三条硬性架构约束

1. **界面绝不直接碰数据库、剪贴板或管线。** 一切经 `Kernel` 的方法调用，
   一切变化经事件订阅回来。这条约束的价值在下一条里立刻体现：
2. **界面可替换。** 内核层完全不 import tkinter。如果下周把界面换成 PySide6，
   改动只发生在 `app/ui/` 目录里，其余代码一行不动。
3. **全离线。** 代码里没有任何 socket / requests / urllib / http 调用。
   用户确认的唯一硬性标准就是这一条。

## 二、五阶段处理管线（对应 TieZ 的 `services/clipboard/pipeline.rs`）

这是整个系统的核心。一次采集从原始数据到入库被拆成五个阶段，
每个阶段读写同一个 `PipelineContext`，任何阶段都可以用
`ctx.should_stop = True` 终止后续阶段。

```
                    ┌─────────────────────────────┐
   系统通知 ───────▶ │ ① DiscoveryStage            │  识别类型（UC-02）
   ClipboardData    │   调 detect_content_type    │  text/rich_text/code/url/image/file
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │ ② TransformationStage       │  规范化 + 脱敏 + 预览 + 图片外置
                    │   · 截断超长内容（10万字）    │  （UC-02 / F2-3 / F9-2）
                    │   · 应用清理规则（正则）      │
                    │   · 敏感识别 → 掩码后再生成预览│
                    │   · 图片：解码→像素指纹→存附件│
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │ ③ ValidationStage           │  回声抑制 + 指纹查重
                    │   先判回声，再查重复          │  （F1-6 / UC-06）
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │ ④ PersistenceStage          │  事务入库 或 合并刷新
                    │   持久化关 → 只进会话内存列表 │  （UC-03 / UC-06）
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │ ⑤ DistributionStage         │  容量裁剪 + 推送事件
                    │   ★ 独立于 stages 列表执行    │  （UC-05 / 7.4）
                    └─────────────────────────────┘
```

### 为什么 ⑤ 不在 `stages` 列表里

这一点在实现过程中踩过坑，值得写下来：

`should_stop` 的语义是"跳过后续**处理**阶段"。
第 ④ 阶段入库完成后会调用 `ctx.stop("inserted")`；
如果 ⑤ 也在 `stages` 列表里，循环开头的 `if ctx.should_stop: break`
会直接把它跳过去 —— 结果是**内容存进库了、界面却永远收不到刷新事件**
（而且容量裁剪也永远不会触发）。

所以 `ClipboardPipeline.__init__(stages, distribution)` 把 ⑤ 单独拿出来，
在循环结束后**无条件执行一次**（只要结果是 inserted 或 merged）。

这个缺陷是被端到端测试抓出来的：容量测试连写 14 条、上限设 10，
库里却实实在在留着 14 条。修完立刻变成 10 条。

## 三、回声抑制（F1-6 / UC-09）

### 问题

用户双击一条历史记录 → 本程序把内容写回剪贴板 → 模拟 Ctrl+V →
**系统通知本程序"剪贴板变了"** → 如果不处理，就会把刚粘出去的内容
当成一次新复制再记一遍。用久了历史里全是自己产生的垃圾。

### 做法：写标记 + 三重比对 + 时间窗

```
粘贴时（严格按 UC-09 业务规则 R1 的顺序）：
    ① dedup.mark_paste(指纹, 内容类型, 原文, 标准化文本, 记录 id)
    ② clipboard_io.write_text(...)          ← 写剪贴板
    ③ 隐藏面板 → 交还焦点 → 发 Ctrl+V        ← 模拟按键

收到剪贴板变化时：
    ① 算指纹 → 与标记比指纹
    ② 原文逐字比
    ③ 标准化后比（覆盖 \n 被系统改写成 \r\n 的情况）
    任一命中且距写入 ≤ 10 秒 → 判定为回声，丢弃本次采集，并**清除该标记**
```

### 两个关键设计点

**为什么不是只比指纹？**
因为"写进去的文本"和"读回来的文本"可能被系统改写过。
实测把 `多行内容\n第二行` 写进剪贴板，读回来会变成 `\r\n`。
只比指纹就会漏判，历史里照样会多一条。

**为什么命中后要清除标记？**
一次粘贴只应被抑制一次。如果标记留着，用户随后**真的**复制同样内容时
会被误杀——那才是更让人困惑的行为（"我明明复制了，怎么没记上"）。
测试里专门有一条断言覆盖这个行为。

**为什么标记不落盘？**
程序重启意味着用户重新开始工作，上一次粘贴的回声不可能跨越重启。

## 四、去重合并（F6 / UC-06）

### 内容指纹

| 类型 | 算法 | 说明 |
|---|---|---|
| 文本类 | 规范化 → BLAKE2b-64bit | 规范化 = 统一换行符 + 全角空格归一 + 去首尾空白 |
| 图片 | 灰度 → 32×32 → BLAKE2b-64bit | 容忍重新编码（PNG 转 JPEG、压缩率变化）带来的字节差异 |

规范化**不折叠中间空白**：代码类内容的缩进是有意义的，
折叠会破坏指纹判别力（UC-02 业务规则 R2：判定为 code 的内容不得被自动改写）。

指纹基于**规范化后的完整内容**，不是预览、也不是前 N 个字符——
UC-06 业务规则 R1 明确禁止只比前缀。测试里专门有一条断言：
两段前 500 字符完全相同、结尾不同的文本，指纹必须不同。

### 合并流程

```
查 (content_type, content_hash) 命中的最新一条
  ├─ 不存在           → 新增记录
  └─ 存在
       ├─ 非图片类再比一次规范化文本
       │    └─ 不同 → 新增记录（指纹碰撞，宁可多一条也不能丢内容）
       └─ 相同 → 合并：id 沿用原记录
                  时间戳 = 本次采集时间
                  使用次数 +1
                  来源应用 = 本次来源
                  ★ 置顶状态、置顶顺序、标签集合 全部保留
```

数据库层用 `idx_history_type_hash` 索引加速指纹查询。

## 五、容量裁剪（F3 / UC-04 / UC-05）

规则写得非常死，因为这个模块最容易"误删用户的东西"：

```
参与计量的条数 N = 总条数 − 豁免条数
    豁免条件：is_pinned = 1  或  tags ≠ '[]'

N > 上限 ？ 否 → 什么都不做
           是 → D = N − 上限
                按 timestamp ASC, id ASC 取最旧的 D 条**未豁免**记录
                逐条删除（记录 + 标签关联）
                事务提交后，再清理这些记录独占的图片附件
```

四条业务规则在代码里都有对应：

| 规则 | 实现位置 |
|---|---|
| R1 严格按时间从旧到新 | `ORDER BY timestamp ASC, id ASC LIMIT ?` |
| R2 置顶与已打标签永不参与 | `WHERE is_pinned = 0 AND (tags = '[]' OR tags = '')` |
| R3 裁剪与附件清理联动，且不得误删共享附件 | `_cleanup_attachments` 先 `COUNT(*) WHERE content = ?` |
| R4 一次入库最多触发一次裁剪 | 只在 DistributionStage 里调一次 `enforce()` |

附件删除有一条安全边界：**只删程序附件目录内的文件**。
用户从桌面复制的原图记的是原路径，那个文件永远不碰。

## 六、Win32 剪贴板读写

### 采集格式优先级（UC-01 主事件流第 4 步）

```
CF_HDROP（文件列表）
  └─ 单个图片文件 → 按图片采集（image）
  └─ 其余         → 按文件采集（file）
CF_DIBV5 / CF_DIB（位图）→ image
"HTML Format"（富文本）  → rich_text（同时保留纯文本作降级）
CF_UNICODETEXT（纯文本） → 走启发式判定：url → code → text
```

一次复制只产生一条记录（UC-01 业务规则 R2），因此这里是"挑一个最合适的格式"，
而不是"把能读的都读出来"。

### 位图处理

剪贴板里的位图是 **DIB**（`BITMAPINFOHEADER` + 可选调色板 + 像素数据），
不是 BMP 文件——它没有 14 字节的文件头。要交给 Pillow 解码必须补回来，
而**补的时候 `bfOffBits` 必须算出真实偏移**：

```python
# bfOffBits = 14（文件头）+ 头长度 + 调色板长度
palette = (clr_used or (1 << bit_count)) * 4 if bit_count <= 8 else 0
file_header = b"BM" + struct.pack("<IHHI", size, 0, 0, 14 + header_size + palette)
Image.open(BytesIO(file_header + dib_bytes))
```

> **这里踩过本项目最严重的一个坑（缺陷 12）。** 早先 `bfOffBits` 被写死成
> 常量 `14`，漏算了位图头长度。Pillow 是认这个字段的，于是它从位图头
> 中间开始读像素，整幅图错位十几个像素、颜色通道全乱。用 1666×1080 的
> 用例图实测：`CF_DIB` 有 **67%** 的像素被改坏，`CF_DIBV5` 有 **47%**——
> 图看起来"还在"，但已经不是原来那张了。
>
> 更值得记的是**为什么一直没被发现**：当时那条图片测试用的是
> `Image.new("RGB", (60, 40), (30, 120, 200))`——一张**纯色图**。
> 纯色图哪怕整体错位几十字节，像素值仍然完全一样，所以断言一直是绿的。
> 现在的 `tests/image_fidelity_check.py` 改用高频细节图案（逐像素变化的
> 颜色 + 奇数宽度覆盖 BMP 行填充），在旧代码上会 100% 报错。

`CF_DIBV5`（`BITMAPV5HEADER`，124 字节）**不需要**特殊处理：Pillow 原生
认识这个头长度，alpha 由它按 `bV5AlphaMask` 自行处理。早先的代码手工把
偏移 52 处的 4 字节掩码删掉，反而让"头长度字段写 124、实际只剩 120"，
雪上加霜。现在 `is_v5` 只用于表达数据来源，解码路径与 `CF_DIB` 完全一致。

### CF_HTML

富文本用 `HTML Format` 私有格式，头部是 `键:值` 文本行，
`StartHTML` / `StartFragment` / `EndFragment` 是**字节**偏移。
中文内容下字符数与字节数不一致，**必须按字节切片**，否则富文本会截断或乱码。
`build_cf_html` 与 `extract_html_fragment` 都按字节处理，测试里有一条
含中文的往返断言守着。

### 线程约定（最容易踩坑的地方）

Win32 对下面三件事都有"必须在建立消息循环的那个线程上调用"的约束：

- `GetForegroundWindow` / `SetForegroundWindow`
- `RegisterHotKey` / `UnregisterHotKey`
- 窗口过程回调

因此 `ClipboardListener` 内部起了一条消息线程，消息窗口、快捷键注册、
来源应用识别全部在该线程上完成。界面线程要改快捷键时，通过队列 +
`PostMessage(WM_APP+2)` 把命令转过去执行。

消息线程**只负责"发现变化 + 取来源快照"，然后立刻把事件抛出去**；
真正的剪贴板读取与入库由 `Kernel` 的工作线程完成。
消息循环一旦被卡住，后面的剪贴板变化通知就会丢。

## 七、粘贴与焦点交还（UC-09）

这是"最容易出现也最影响体验的缺陷"（UC-09 业务规则 R4 原话）。

### 完整顺序

```
界面：show() 时**先**记下当前前台窗口句柄
      （必须早于 Tk 拿到焦点，晚一步记下来的就是面板自己）
        ↓
用户双击记录 → Kernel.paste_entry()
        ↓
① 写粘贴标记          dedup.mark_paste(...)
② 写剪贴板            write_text / write_text_and_html / write_image / write_files
③ 隐藏面板            面板 withdraw（焦点此时回到用户原来的应用）
④ 交还焦点            paste.restore_foreground_window(目标句柄)
⑤ 等 60ms + 90ms      让目标应用完成激活
⑥ 发 Ctrl+V           paste.send_key_combo(VK_V, MOD_CONTROL)
```

### 位图粘不进文件夹，以及「复制为文件」（UC-09 备选流 A4）

图片记录在第 ② 步走的是 `write_image()`，写上去的是 `CF_DIB`（位图）。
这对接"粘贴到画图 / Word / 微信"是对的，但**粘到文件夹里不会有任何反应**。

这不是程序的缺陷，是 Windows 的规矩：资源管理器只接受 `CF_HDROP`
（文件列表），它不会把剪贴板里的位图落成一个文件。做了对照实验：

| 剪贴板内容 | 在文件夹里按 Ctrl+V |
|---|---|
| `CF_DIB`（位图） | 什么都不生成 |
| `CF_HDROP`（文件路径） | 生成该文件的副本，字节与源文件完全一致 |

所以右键菜单在图片记录上多给了**「复制为文件（可粘贴到文件夹）」**：
把附件 PNG 的路径用 `write_files()` 放上剪贴板，之后在任意文件夹里
`Ctrl+V` 就能直接得到图片文件。

要注意 `CF_HDROP` 里的 `.png` **会被自己重新采集一遍**（采集优先级里
文件列表排第一，单个图片文件按图片入库），所以这条命令和 `paste_entry`
一样，必须在写剪贴板**之前**登记回声标记，否则粘一次就多一条记录。

### 焦点交还的四级策略

`SetForegroundWindow` 有一条很烦的限制：只有"调用进程当前拥有前台窗口"
等少数情况才会成功。而且**返回成功也不代表真的切过去了**——
它会只闪一下任务栏图标。

```python
① 直接 SetForegroundWindow
② Alt 键技巧：keybd_event(VK_MENU) 按下+抬起
   → 让系统认账"本进程刚收到过用户输入"，这是 Windows 的明文放行条件
③ AttachThreadInput 把本线程输入队列附加到目标线程再切
④ ShowWindow(SW_MINIMIZE) → 稍等 → SW_RESTORE，强制顶到最前
```

每步之后都用 `get_foreground_window()` 复核是否真的切过去了
（这是关键——只看返回值会误判），任一步确认成功即返回。
`AttachThreadInput` 必须成对解除，否则会挂住两边的输入处理。

实测覆盖：前台窗口是浏览器（本 GUI）、真实记事本、本程序自己的窗口，
连续三轮全部成功。

### 模拟按键为什么用 keybd_event 而不是 SendInput

**这是实测结论，不是偏好**：

本机用 `SendInput` 发 Ctrl+V 时，返回值报告 4 个事件全部发出、
`GetLastError` 为 0，但记事本、浏览器等目标窗口**收不到任何内容**；
换成 `keybd_event` 立刻正常，重复三轮都成功。

两套 API 的结构体与参数都反复核对过：
`KEYBDINPUT` 各字段偏移正确，`cbSize` 也已按
"最大联合成员 MOUSEINPUT 决定 INPUT 大小"这一规则修正为 40
（用 `ctypes.sizeof(INPUT)` 会得到 32，传 32 会被系统以
`ERROR_INVALID_PARAMETER(87)` 拒绝，**一个按键都发不出去**）。

因此判断问题出在 `SendInput` 与 ctypes 联合体布局的配合上。
工程取舍：粘贴是这个软件最核心的链路，"能不能粘上"远比"用哪个 API"重要，
所以主路径用实测可用的 `keybd_event`；
`SendInput` 版本保留为 `send_key_combo_sendinput`，方便后续验证与切换。

## 八、内容类型判定（F4-1 / UC-02 第 5 步）

严格照 UC-02 主事件流实现，同时补了一条需求文档没写、但实测必须加的规则。

```
① 位图 / 图片文件          → image
② 文件路径列表             → file
③ HTML 富文本              → rich_text（保留 HTML 原文）
④ 纯文本启发式：
   4.1 以 www. 开头，或含 :// 且协议合法，且整段无空白 → url
   4.2 代码特征得分 ≥ 2        → code
       命中关键字各 +1；含分号 +1；含花括号 +1；含 </ 与 > +2
   4.3 以 { 开头、以 } 结尾且同时含冒号与双引号 → code（覆盖 JSON 片段）
   4.4 其余                    → text
```

### 补的那条规则：自然语言否决

需求文档的 4.2 会让这句话被判成代码：

> 请把 return 的结果发我，谢谢。

它命中了 `return `（+1分）和 `;`（不，中文分号不算）…… 实际是命中了
`return ` 关键字，但只有 1 分，所以勉强过关。真正会误判的是这类：

> 这个函数用 const 定义，然后 if 一下就行，我觉得可以。

命中了 `const ` 和其他关键字，得分 ≥ 2，被误判为代码。

而 UC-02 业务规则 R1 明确要求"类型判定必须与实际内容一致，
不允许出现'内容明显是代码却标为文本'的情况"——反过来同样成立。

因此加了一条**否决条件**：命中中文标点（。，、；？！""《》）的内容，
或者"单行、有空格、无分号、无代码符号的长句"，直接否决代码判定。
测试里专门有一条断言守着这个行为。

## 九、隐私（F9-1 / F9-2）

### 识别规则

| 类型 | 正则要点 | 掩码规则 |
|---|---|---|
| 身份证 | 18 位，末位可为 X，前后加字母数字边界 | 保留前 6 后 4 |
| 手机号 | 11 位，1 开头，第二位 3~9，前后加数字边界 | 保留前 3 后 4（`138****5678`） |
| 邮箱 | 用户名 @ 域名.后缀 | 保留用户名首字符 + 完整域名 |
| 密钥 | `sk-` `ghp_` `AKIA` 等常见前缀令牌；32 位以上长随机串；PEM 私钥标记 | 只显示前缀与长度 |

纯数字的长串（例如一段很长的编号）会被排除在"密钥"之外，
否则会把正常内容大面积误脱敏（UC-17 异常流 E1 的误判问题）。

### 脱敏时机

脱敏发生在**入库前的预览生成阶段**（TransformationStage）：
先扫描 → 生成掩码文本 → 再折叠空白与截断 → 写进 `preview` 字段。

原文照旧存 `content` 字段，用户主动点开时能看到全文——
UC-17 业务规则 R3 明确要求这一点，否则功能就从"隐私保护"变成"内容丢失"。

### 本期边界（如实说明）

**加密落盘（F9-3）尚未实现，敏感内容在数据库中仍是明文。**
本阶段只做到"识别 + 列表脱敏显示"。设置面板里也是这么写的，
`is_sensitive` 字段已经落库，下周接入加密时不需要再走一次结构升级。

## 十一、窗口形态与"关掉终端还能用"

### 面板为什么是标准窗口而不是无边框浮层

最初面板用 `overrideredirect(True)` 做成了无边框浮层 —— 视觉上更像
"呼出式面板"，但它**没有标题栏**，于是用户既不能拖动它、也不能最小化或
关闭它。这是设计上的失误：剪贴板管理器每天要开几十次，
"能不能挪开、能不能缩起来"直接影响可用性。

现在改成标准 Windows 窗口（即 `overrideredirect(False)`），得到：

| 能力 | 来源 |
|---|---|
| 拖动移动 | 系统标题栏 |
| 缩放改大小 | `WS_THICKFRAME` + `resizable(True, True)` |
| 最小化 | 标题栏按钮 + 面板内 `—` + `Ctrl+M` |
| 关闭 | 标题栏 ✕ + 面板内「收起」+ `Ctrl+W` + `Esc` |

### 关闭按钮的语义：收起面板，不是退出程序

`WM_DELETE_WINDOW` 绑到 `hide()` 而不是退出。理由：

1. 剪贴板管理器**必须常驻**才能记录，误关一下就退出会让用户莫名其妙地
   发现"怎么不记了"；
2. 托盘图标与全局快捷键的存在意义就是"随时唤出来"，
   如果关闭即退出，这两条入口同时失效；
3. 真正退出的入口放在**托盘右键 → 退出**，语义明确、不容易误触。

设置面板里也写清了这一点，避免用户以为程序已经关了。

### 尺寸记忆：只记大小，不记位置

`<Configure>` 事件在窗口每次移动/缩放时都会触发。如果直接在里面写数据库，
拖动窗口就变成高频写库。所以：

- `<Configure>` 里只更新一个内存变量 `_last_geometry`；
- 真正落库发生在 `hide()` 里，一次隐藏只写一次；
- 窗口处于 `iconic`（最小化）状态时上报的尺寸是无效值，必须跳过 ——
  否则最小化一次就会把尺寸记成 1x1。

**只记大小不记位置**：面板是"停靠式"工具，固定在屏幕中上部弹出来更好预期；
如果把位置也一起记，用户偶尔把窗口拖到副屏、下次在单屏环境下打开，
窗口就会出现在屏幕外，反而更难用。

### 从最小化唤出必须先还原状态

`withdraw()` 过的窗口再 `deiconify()` 会**保持图标化**，
必须显式 `state("normal")` 才能真的显示出来。
所以 `show()` 里是"先 deiconify，再判断是否 iconic 并还原"这一串，
少写一行就会出现"按了快捷键、任务栏图标闪一下、窗口没出来"。

### 关掉终端为什么程序会退出，以及怎么解决

这是 Windows 的规则，不是 Python 的毛病：

> 控制台程序（`python.exe`）与控制台窗口是**绑定**的。关掉控制台时，
> 系统向该控制台里的所有进程发送 `CTRL_CLOSE_EVENT`，
> 进程随后被结束 —— 快捷键注册与托盘图标自然也一起消失。

于是"关掉终端后快捷键还能用"这个需求，本质上是"**让程序脱离控制台**"。
实测了三种做法：

| 方式 | 控制台关闭后存活 | 说明 |
|---|---|---|
| 普通 `subprocess` 启动 `python.exe` | ❌ | 随控制台一起被杀 |
| `DETACHED_PROCESS` 启动 `python.exe` | ✅ | **最终采用** |
| 启动 `pythonw.exe` | ⚠️ | 需要脚本路径全 ASCII |

`pythonw.exe` 的坑很具体：当时项目目录还叫 `开发`（含非 ASCII 字符），
实测 `pythonw.exe "G:\soft\Paste PRO\开发\app\main.py"` 会以退出码 2
直接失败 —— 命令行里的非 ASCII 路径解析出问题；
同样路径下 `DETACHED_PROCESS` 方式工作正常。

> **项目目录后来已改名为 ASCII 的 `1st`**，`pythonw` 现在也能用了，
> 但启动器**仍然沿用 `DETACHED_PROCESS`**：它对路径不做任何假设，
> 将来谁把目录改成中文名也不会突然启动失败。
> 这也正是把目录改名的一个附带好处 —— 非 ASCII 路径在 Windows 上
> 是一类反复出现的坑（`pythonw` 的参数解析、部分工具链的编码处理等）。

最终结构：

```
启动剪贴板Pro.bat          ← 前台：检查依赖、打印提示，显示完自动关闭
      └─ 启动剪贴板Pro.py  ← 用 DETACHED_PROCESS 启动内核，报告 pid 后自己退出
            └─ python -m app.main   ← 后台驻留，托盘 + 全局快捷键
```

### pythonw 兼容性：两处必须做的适配

程序可能在无控制台环境下运行，为此在 `main.py` 最早期做了两件事：

1. **兜底 stdout / stderr。** `pythonw` 下这两个是 `None`，
   任何一处 `print` 或 `logging` 打屏都会抛 `AttributeError` 把程序带崩。
   因此 `_harden_streams()` 在**任何 print / logging 之前**执行，
   把不可用的流替换成哑对象。
2. **单实例守卫放在最前面**（见下）。

### 单实例守卫：为什么必须有

程序改成后台驻留后，用户看不到任何窗口，很容易以为没启动成功而反复双击。
后果不是"多开几个窗口"这么轻：

> `RegisterHotKey` 是**先到先得**的 —— 第二个实例拿不到快捷键，
> 却仍然占着托盘图标。表现就是"点了几次之后快捷键时灵时不灵"。

因此用进程级命名互斥体（`CreateMutexW`）做守卫。选它的理由：

- 互斥体随进程结束**自动释放**，不存在"程序崩了留下锁文件导致再也起不来"；
- 不需要联网、不占端口、不写 PID 文件。

第二个实例的行为：尝试把已有实例的面板唤到前台（用第九章那套四级焦点策略），
唤不动就弹一个系统消息框说明情况，然后以退出码 3 退出。
这里刻意**不承诺一定能唤起** —— 跨进程 `SetForegroundWindow` 本来就
常常被系统拒绝，与其假装成功，不如老实引导用户按快捷键或点托盘图标。

---

### 快捷键被占用：候选降级 + 写回配置

`RegisterHotKey` 是先到先得的，而 `Ctrl+Shift+V` / `Ctrl+Shift+F`
是最抢手的组合之一。实测本机这两个键**都已被别的程序占用**
（`GetLastError` = 1409 `ERROR_HOTKEY_ALREADY_REGISTERED`）。
只试一个组合就放弃，用户拿到的体验就是"快捷键是坏的"。

所以每个动作配一组候选，按顺序尝试：

```
main_panel: Ctrl+Shift+V → Ctrl+Alt+V → Ctrl+Shift+F9 → Ctrl+Shift+F10 → …
search    : Ctrl+Shift+F → Ctrl+Shift+S → Ctrl+Alt+F → Ctrl+Shift+F8 → …
```

发生降级时要做三件事，缺一件用户就会困惑：

1. **写回配置** —— 面板状态栏与设置界面读的都是配置值，
   不写回的话它们会一直显示那个**按了没反应**的旧键；
2. **弹一次提示** —— 明确告诉他"X 被占用了，已改用 Y"；
3. **在设置面板里标出来** —— 显示 `（Ctrl+Shift+V 被占用，已自动改用此键）`。

一个边界：**用户手动在设置里指定的键不做降级**。
那是明确意图，系统悄悄换成别的组合反而会让人以为设置没生效；
此时只报告失败并保留原键。

全部候选都失败时，提示必须**可执行**：
"请点击托盘图标，并在设置 → 快捷键里换一个组合" ——
而不是一句"注册失败"。

### 事件轮询必须常驻（这是踩过的坑）

界面与内核是"事件队列 + 定时消费"的结构：
`_poll_events()` 每 120ms 跑一次，把内核事件转成界面动作。

最初的实现是"面板显示时启动轮询、隐藏时停止" —— 听起来很合理（省 CPU），
但它制造了一个死锁：

> 面板隐藏 → 停轮询 → 快捷键事件没人消费 → 面板永远唤不出来

而且这个缺陷只在"隐藏状态下按快捷键"这一条路径上暴露：
启动时带 `--show` 面板是显示的，轮询在跑，看起来一切正常；
用户一旦收起面板，快捷键就**永久**失效了。

现在轮询在构造面板时就启动、只在程序退出时停止。
隐藏状态下照样消费事件，只是**不重绘列表**（那才是真正费 CPU 的部分）。

配套还有一个 350ms 的"刚隐藏"抑制窗口：避免用户按 `Esc` 收起面板的瞬间，
上一轮积压的唤出事件在 120ms 后被应用上去，面板又自己弹回来，
看起来像"关不掉"。

分四层，越往下越接近真机：

| 层 | 脚本 | 特点 |

| 静态 | `static_check.py` | AST 遍历找"用了但没定义"的名字。**是被真实缺陷逼出来的**——开发中先后出现过 `human_size` 与 `K_LIST_DENSITY` 两处忘记导入，都只在某条分支上才炸 |
| 启动脚本 | `check_launchers.py` | 硬检查 `.bat` 的换行符与编码。**同样是被真实事故逼出来的**（缺陷 9：LF 换行导致双击一闪就没） |
| 仓储 | `smoke_repository.py` | 建库、CRUD、检索、排序、裁剪、标签，29 项 |
| 端到端 | `e2e_pipeline.py` | 用 `simulate_capture` 绕过真实剪贴板，把管线跑完整，65 项 |
| 界面 | `ui_smoke.py` | 真实创建 tkinter 窗口、渲染、切换主题、注入事件，30 项 |
| 快捷键 | `hotkey_check.py` | 候选降级、隐藏态唤出、托盘命令派发，**并发真实按键做端到端验证**，28 项 |
| 窗口行为 | `window_behavior_check.py` | 查 Win32 样式位确认标题栏存在；验证关闭=收起、最小化/还原、尺寸记忆；并用真实脱离控制台的子进程验证"终端关掉后仍存活"，41 项 |
| 真机 | `manual_*.py` | 真实注册监听、真实写剪贴板、真实注册快捷键、真实往记事本粘贴，37 项 |

真机测试用了一个关键技巧：**三层递进的目标窗口**
（Tk 自建窗口 → 真实记事本 → `WM_GETTEXT` 读回验证）。
只用 Tk 窗口时测试会骗人——Tk 有自己的焦点模型，

所以最后一定要用系统记事本这种标准 Win32 编辑控件来收尾验证。
