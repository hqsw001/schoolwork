## 三、开发过程中发现并修复的真实缺陷

按发现顺序记录，这些都是**测试真的抓出来的**，不是走过场。

### 缺陷 1：分发阶段永远不会执行（严重）

- **现象**：容量上限设为 10，连写 14 条，库里实实在在留着 14 条，一条没删。
- **定位**：`ClipboardPipeline.execute` 的循环开头有 `if ctx.should_stop: break`。
  入库阶段完成后会调用 `ctx.stop("inserted")`，于是紧随其后的分发阶段
  （容量检查 + 事件推送）**被直接跳过**。
- **影响**：不止容量裁剪失效——**界面也永远收不到 `clipboard-updated` 事件**，
  意味着复制之后列表不会自动刷新。这是"看起来在跑但界面不动"的严重问题。
- **修复**：把分发阶段从 `stages` 列表里拿出来，作为 `distribution` 参数传入，
  在循环结束后无条件执行一次。
- **验证**：修复后容量测试 3 项断言全部通过；界面冒烟的"事件推送驱动刷新"也通过。

### 缺陷 2：`human_size` 未导入（内部错误）

- **现象**：打开设置面板看容量统计时报"内部错误：name 'human_size' is not defined"。
- **定位**：`capacity.py` 的 `stats()` 里在函数内部 `from ... import human_size`，
  但代码路径上并未导入（写成了一行注释掉的历史导入）。
- **修复**：改为模块级导入。
- **衍生**：写 `static_check.py` 专门防这类问题，并纳入一键回归。

### 缺陷 3：`K_LIST_DENSITY` 未导入（内部错误）

- **现象**：在设置里切换列表密度（紧凑/标准/宽松）时报同样的未定义错误。
- **定位**：`kernel.py` 的常量导入清单里漏了这一项。
- **修复**：补上导入。
- **验证**：界面冒烟新增"三档列表密度切换后都正确生效（含行内边距）"断言。

### 缺陷 4：`SendInput` 报告成功但按键没送达（严重）

- **现象**：双击记录后面板正常隐藏、焦点正常交还，但记事本里什么都没粘上。
- **定位过程**：
  1. 先加日志，发现 `send_key_combo` 返回 False，日志里是
     `SendInput 只发出 0/4 个按键事件（err=87）` —— err 87 = `ERROR_INVALID_PARAMETER`。
  2. 打印结构体布局：`sizeof(INPUT) = 32`，而 Win32 头文件里 `INPUT` 的大小
     由最大联合成员 `MOUSEINPUT`（32 字节）决定，加上 `type` 字段与对齐后是 **40**。
     ctypes 只实例化了 `KEYBDINPUT` 成员，自然对齐后得到 32，传 32 被系统拒绝。
  3. 改成 40 之后 `SendInput` 返回 4/4、err 0 —— **但记事本里依然什么都没粘上**。
  4. 做对照实验：同样场景改用 `keybd_event` 发 Ctrl+V，立刻成功。
- **结论**：`SendInput` 与 ctypes 联合体布局的配合有问题（返回成功但不投递），
  两套 API 的参数都已反复核对过。
- **修复**：粘贴主路径改用实测可用的 `keybd_event`；
  `SendInput` 版本保留为 `send_key_combo_sendinput` 便于后续验证与切换。
  同时在 `win32.py` 里把 `INPUT_SIZE_X64 = 40` 写成带说明的常量，
  避免下次有人"顺手改成 `sizeof(INPUT)`"又踩一遍。

### 缺陷 5：焦点交还失败导致粘贴丢失（严重）

- **现象**：测试里 `SetForegroundWindow` 返回成功，前台窗口却没变，
  结果 Ctrl+V 打到了浏览器上。
- **定位**：`SetForegroundWindow` 的经典限制——只有"调用进程当前拥有前台窗口"
  或"刚收到过用户输入"等少数情况才会真的切换；
  而且**返回成功也可能只是闪一下任务栏图标**，不能只看返回值。
- **修复**：改成四级递进策略，并且**每一步之后都用 `get_foreground_window()` 复核**：
  1. 直接 `SetForegroundWindow`
  2. Alt 键技巧（`keybd_event(VK_MENU)` 按下+抬起，让系统认账"刚有用户输入"）
  3. `AttachThreadInput` 附加输入队列后再切
  4. `ShowWindow(SW_MINIMIZE)` → 稍等 → `SW_RESTORE`
- **验证**：连续三轮真机压力测试（前台窗口是浏览器的情况下切到新启动的记事本），
  每一轮 `activate=True fg_ok=True send=True pasted=True`。

### 缺陷 6：对话框阻塞式等待导致测试死锁（中等）

- **现象**：界面冒烟测试跑编辑器对话框时整个进程挂住，180 秒超时。
- **定位**：`EditorDialog.__init__` 里调了 `self.wait_window(self)`，
  而 `wait_window` 依赖事件循环分发 Destroy 事件。
  在窗口尚未映射的时刻被程序化调用时会直接死锁。
  快捷键录制器 `_HotkeyRecorder.capture` 有同样的问题。
- **修复**：两个对话框都改成**回调式**（传 `on_save` 回调，`destroy()` 后回调），
  不再阻塞等待。顺带避免了"对话框没关就点别的"这类焦点问题。
- **附带**：`GetWindowText` 读回文本时 `lParam` 传 `c_void_p` 会被 ctypes 拒绝，
  必须传指针的整数值（`ctypes.cast(buf, c_void_p).value`）。

### 缺陷 7：`EnumWindows` 回调签名错误（测试脚本）

- **现象**：找记事本窗口时刷了几百行 ctypes 回调异常。
- **定位**：`EnumWindows` 的回调签名是 `(HWND, LPARAM) -> BOOL`，
  和窗口过程 `(HWND, UINT, WPARAM, LPARAM) -> LRESULT` **不是一回事**。
  先前复用了 `WNDPROCTYPE`，导致"takes 2 positional arguments but 4 were given"。
- **修复**：在 `win32.py` 里单独定义 `WNDENUMPROC = WINFUNCTYPE(BOOL, HWND, LPARAM)`
  并用于 `EnumWindows` / `EnumChildWindows`。

### 缺陷 8：`SW_RESTORE` 常量缺失（中等）

- **现象**：焦点交还时报 `'NoneType' object cannot be interpreted as an integer`。
- **定位**：`win32.py` 里没定义 `SW_RESTORE`，取到的是 `None`，
  ctypes 在转换参数时抛出这个难以定位的类型错误。
- **修复**：补齐 `SW_*` 常量族；
  加了一条防呆断言，避免"少写一行常量"又变成运行时崩溃。

### 缺陷 9：启动器 `.bat` 使用 LF 换行导致完全失效（严重，用户现场报障）

- **现象**：用户双击 `启动剪贴板Pro.bat`，**黑窗口一闪就消失、程序没启动**；
  随后按 `Ctrl+Shift+V` 自然也没有任何反应。
- **定位过程**：
  1. 先确认程序本身没问题——直接用 `python -m app.main --show` 启动正常，
     面板窗口存在且可见。问题锁定在 `.bat` 本身。
  2. 读文件字节：UTF-8 无 BOM，**41 个换行全是孤立 LF（CRLF = 0）**。
  3. 把该文件原样喂给 `cmd /c` 跑，输出暴露了真相：

     ```
     'mport' is not recognized as an internal or external command
     'pywin32' is not recognized as an internal or external command
     '...系统托盘）...' is not recognized as an internal or external command
     ```

     中文被拆成乱码片段、`python -m pip install` 被拆成了 `'mport'` 与
     `'pywin32'` —— **行与行之间被"粘"在了一起**。
  4. 做编码矩阵实验（4 种编码/代码页组合 × 2 种行尾）：

     | 行尾 | 编码 / chcp | 结果 |
     |---|---|---|
     | CRLF | gbk / utf8 × chcp 开 / 关 | **4 种全部正常** |
     | LF | gbk / utf8 × chcp 开 / 关 | **4 种全部报错** |

- **根因**：`cmd.exe` 解析 `.bat` 时**不认孤立的 LF（0x0A）行尾**。
  文件里只要含中文这类多字节字符，cmd 就会判断错行尾、继续往后读，
  把下一行粘到上一行上。于是 `python -m app.main` 这一行被当成上一条
  `echo` 的参数吞掉，程序从未启动，脚本自己走到 `exit /b` 结束。
  **与文件编码无关、与 `chcp 65001` 无关，只取决于行尾。**
- **修复**：
  1. 把 `.bat` 整个转成 CRLF 换行。关键教训：**写文件工具默认产出 LF**
     （对 `.py` 完全正确，对 `.bat` 是致命的），生成 `.bat` 之后必须显式转一次；
  2. 重写启动器：用 `goto` 标签式流程替代嵌套括号块；
     `title` 改成 ASCII 的 `ClipboardPro`（原本的 `title 剪贴板Pro` 会让控制台
     窗口与程序面板同名，排查时极易混淆）；程序异常退出时打印退出码与日志路径；
  3. 新增 `tests/check_launchers.py` 硬检查：孤立 LF、UTF-8 BOM、
     非 ASCII 字符是否落在安全命令里，并做了正反双向验证
     （正常文件通过、故意造的 LF 版本必须报错）；
  4. 新增 `.gitattributes`，为 `*.bat` / `*.cmd` 声明 `eol=crlf`，
     防止 Git checkout 时再被改回 LF；
  5. 把该检查并入 `run_tests.py`，每次回归都会跑。
- **验证**：用 `cmd /c` 模拟双击，启动器完整走完 `[1/3] [2/3] [3/3]`
  并成功拉起程序（检测到可见的 `ClipboardPro` 面板窗口）。

> **这个缺陷值得单独记一段**，因为它有三个"没想到"：
> 一是没想到纯文本的换行符能决定一个启动脚本的生死；
> 二是没想到生成文件的工具会默认写 LF，而这对 `.bat` 是致命的；
> 三是没想到失败方式是**静默的**——脚本没有报错退出，而是自己跑完了，
> 现场只看到"闪一下"，没有任何线索可循。
> 所以这次补的是**机制**（检查脚本 + `.gitattributes` + 纳入一键回归），
> 而不只是把那个文件改对。

### 缺陷 10：面板隐藏后事件轮询被停掉，快捷键彻底失效（严重，用户现场报障）

- **现象**：用户报告"按 Ctrl+Shift+V 呼不出面板，托盘也没任何作用"。
- **定位过程**：
  1. 先看现场：日志显示程序**正在运行**、快捷键**注册成功**、
     粘贴功能也正常（有一次真的把内容粘出去了）。
     说明问题不在注册，也不在程序没起来。
  2. 写了一个探针，把测试窗口挂到监听窗口上（用 `EnumThreadWindows`，
     因为消息窗口 `HWND_MESSAGE` 不会被 `EnumWindows` 枚举到），
     然后手动投递 `WM_HOTKEY`，并在**每一个环节**插桩打印。
  3. 插桩结果一目了然：

     ```
     面板显示时投递：  [panel._handle_event] action=toggle_panel → 收起 ✅
     面板隐藏后投递：  [listener.poll_events] -> [('hotkey', ...)]
                       [handle_listener_events] 处理前队列=1
                       （之后再无输出）              ← 事件在这里断了
     最终 visible = False
     ```

- **根因**：`MainPanel.hide()` 调用了 `_stop_polling()`，而事件轮询是
  **唯一**把内核事件转成界面动作的通道（`_poll_events` → `_handle_event`）。
  于是形成死锁：

  > 面板隐藏 → 停轮询 → 快捷键事件没人消费 → 面板永远唤不出来

  更糟的是这个缺陷**只在"隐藏状态下按快捷键"这一条路径上暴露**：
  启动时带 `--show` 面板是显示的，轮询在跑，看起来一切正常；
  用户一旦收起面板，快捷键就永久失效了。
- **修复**：
  1. 事件轮询改为**常驻**：构造面板时就启动，只在程序退出时停止
     （`hide()` / `minimize()` 都不再停它）；
  2. `_handle_event` 改为"始终处理事件，但隐藏时不重绘列表"，
     兼顾"能唤出"和"不浪费 CPU"；
  3. 顺带修掉一个相关的体验问题：加了 350ms 的"刚隐藏"抑制窗口，
     避免收起面板的瞬间又被上一轮积压的唤出事件弹回来。

### 缺陷 11：快捷键被占用后只弹一个没人看得到的提示（严重，用户现场报障）

- **现象**：与缺陷 10 同时被报告，"快捷键仍然不起作用"。
- **定位过程**：写了一个注册矩阵探针，逐个尝试常见组合并读 `GetLastError`：

  | 组合键 | 结果 |
  |---|---|
  | `Ctrl+Shift+V` | ❌ 被占用（err=1409 `ERROR_HOTKEY_ALREADY_REGISTERED`）|
  | `Ctrl+Shift+F` | ❌ 被占用 |
  | `Win+Shift+V` | ❌ 被占用 |
  | `Ctrl+Shift+F9` / `Ctrl+Shift+F10` / `Ctrl+Alt+V` / `Ctrl+Shift+Alt+V` / `Ctrl+Alt+Q` / `Ctrl+F9` | ✅ 空闲 |

  也就是说：**配置里的默认键在本机根本注册不上**。而旧实现只试这一个组合，
  失败后仅发一个 `EVENT_ERROR` 事件——它被转成界面 toast，
  但那时面板还是隐藏的（缺陷 10 导致隐藏时不消费事件），
  用户**从头到尾没看到任何提示**，只感觉"快捷键是坏的"。
- **修复**：
  1. 每个动作配一组**候选快捷键**，按顺序尝试，用第一个能注册成功的；
  2. 发生替换时：写回配置（否则界面还显示那个按了没反应的旧键）、
     弹提示说明实际生效的是哪个键、并把新键显示在状态栏与设置面板里；
  3. 全部候选都失败时，给出**明确可执行的**错误提示
     （"请点击托盘图标，并在设置→快捷键里换一个组合"），而不是静默；
  4. 用户手动在设置里指定的键**不做降级** —— 那是明确意图，
     悄悄换成别的组合反而会让人以为设置没生效。
- **验证**：新增 `tests/hotkey_check.py`（28 项），其中最后一项是
  **真按键验证** —— 撤掉自己的注册后真的把组合键发出去，
  确认系统把按键送到了监听窗口、面板被唤出。
  连续按三次的结果：`VISIBLE → hidden → VISIBLE`，开关行为正确。

> **这两个缺陷是一起被发现的，但成因完全不同**：
> 一个是**架构性**的（事件通道被自己关掉了），
> 一个是**设计假设**错了（以为默认快捷键一定注册得上）。
> 前者说明"只测显示状态"是不够的 —— 隐藏状态才是这个产品的常态；
> 后者说明"注册失败"这种事必须让用户**看得见**，否则等价于功能损坏。
> 现在两条路径都被 `tests/hotkey_check.py` 守住。

> **附带的教训：非 ASCII 路径。**
> 排查过程中还发现 `pythonw.exe` 在含中文的路径下会以退出码 2 直接失败
> （`pythonw.exe "G:\soft\Paste PRO\开发\app\main.py"`）。
> 应要求已把项目目录从 `开发` 改名为 `1st`，
> 消掉了这一类反复出现的坑（`pythonw` 参数解析、部分工具链的编码处理等）。
> 启动器仍然坚持用 `DETACHED_PROCESS` 而不是 `pythonw`，
> 因为它对路径不做任何假设 —— 将来谁再把目录改成中文名也不会突然失败。


### 缺陷 12：`bfOffBits` 写死成 14，所有位图采集出来的图都是错的（严重，用户现场报障）

- **现象**：用户复制了一张用例图，问"图片怎么粘贴出来"。把库里那条图片附件
  和磁盘上的原图一比，尺寸一样（1666×1080）、肉眼看着也像，但
  **47% 的像素不一样**，最大通道差 255。
- **定位**：拿系统解码器（`PIL.ImageGrab.grabclipboard()`）当基准去比
  `image_utils.dib_to_image()`，做成对照表：

  | 解码方式 | 与系统解码的差异 |
  |---|---|
  | 源图本身 | 0 像素 ✅ |
  | `dib_to_image(CF_DIB)` | 1 215 396 像素 ❌（67.55%）|
  | `dib_to_image(CF_DIBV5)` | 851 745 像素 ❌（47.34%）|
  | 原样 + `bfOffBits=54`（CF_DIB） | 0 像素 ✅ |
  | 原样 + `bfOffBits=138`（CF_DIBV5） | 0 像素 ✅ |

- **根因**：两个错误叠在一起。
  1. 补 BMP 文件头时把 `bfOffBits`（像素数据偏移）写成了常量 `14`，
     而它必须是 `14 + 头长度 + 调色板长度`。Pillow 认这个字段，于是从
     位图头中间开始读像素，整幅图错位十几个像素、颜色通道全乱。
  2. 为了处理 `CF_DIBV5` 的 alpha 掩码，手工把偏移 52 处的 4 字节删掉，
     但头长度字段仍然写着 124、实际只剩 120 —— 又一次错位。
     Pillow 本来就认识 124 字节的 `BITMAPV5HEADER`，这一步纯属多余。
- **修复**：`bfOffBits` 按 `14 + header_size + palette` 计算；去掉 alpha
  掩码的手工剔除；顺带把 ≤8 位色深的调色板长度算进去（8 位图会多出
  1024 字节调色板）。修完同一张图的差异降到 **0 像素**。
- **为什么长期没被发现**：`manual_clipboard_check.py` 第 4 节的图片用例是
  `Image.new("RGB", (60, 40), (30, 120, 200))` —— **一张纯色图**。
  纯色图整体错位几十字节之后，像素值仍然完全一样，断言一直是绿的。
  换句话说，**测试用例的取值把这个缺陷屏蔽掉了**。
- **回归**：新增 `tests/image_fidelity_check.py`（22 项），用 97×61 的
  逐像素变化图案。已验证该套件在修复前的代码上 100% 报错、修复后全绿。

> 这条缺陷同时说明了"顺着用户的一句话往下查"的价值：用户只是问了一句
> "图片怎么粘出来"，顺着这个问题去比对才发现，**库里存的图早就不是他
> 复制的那张了**。

## 五、怎么复现这份报告

```bat
cd 1st

:: 全部套件（会短暂弹窗、占用系统剪贴板、启动一个记事本并自动关闭）
python run_tests.py --all

:: 只跑不碰系统剪贴板的部分
python run_tests.py --safe

:: 单跑某一个套件（能看到全部断言明细）
python tests/e2e_pipeline.py
python tests/manual_notepad_paste.py
```
